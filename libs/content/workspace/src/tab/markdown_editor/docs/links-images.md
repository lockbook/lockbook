# Links and images
A link goes to another Lockbook file or a web URL. Syntax is a normal markdown link, wiki link, or autolink; an image is a markdown image or a wiki embed. On open, a Lockbook file stays in the app, while a web URL resolves through the host system.

## Scope
A link means the same file, or fails the same way, for everyone who can read the note. A note's scope is the subtree of its innermost shared ancestor (the whole tree for a note under no share), and relative paths and wiki titles resolve inside it: wiki titles match below the top, nearest first, and as in Obsidian only `.md` may be left off (`[[Plan]]` is `Plan.md`, a drawing is `[[Sketch.svg]]`); equally near matches are a tie, which resolves to nothing. Inside the scope, where a recipient places a share changes nothing.

Green links open the same file for everyone who can read the note. Yellow links open different things for different people, so they ask first. Red links open nothing. Images are the same three: a green image shows, a yellow one is hidden like a spoiler (an eye-slash, "Click to show", a yellow dot) because in a write share a collaborator may have put a file of *yours* here; a tap shows it, and the picture then says nothing more; a red one has a red dot and shows why nothing resolves.

Green is anything found inside the scope, and an absolute path in a note no one else reads. Yellow is a relative path or wiki title found only past the scope, anywhere in the reader's files, an id link (`lb://<id>` or `https://app.lockbook.net/open/<id>`) to a file outside the scope, and an absolute path in a shared note, which each reader resolves from their own root. Yellow asks the owner too: with write access, anyone can add links to a note. Red is anything that resolves to nothing, which is never handed to the operating system.

## Writing links
A link can be typed by hand or picked. `[[`, `[`, `![`, or `](` opens a picker over the files the note can link to: those in its scope first, ranked by how the name matches what was typed (starts with it, then contains it, then has its letters in order along the path from the note), then by folders from the note, then by name. Within each class nearer files come first, then by name, so typing more can only drop or demote the files below the top one, never move them past it. Files outside the scope follow under a rule with a dot before their crumbs in the color the link will be drawn in: yellow where it reaches the file for this reader past the scope, red where nothing will (a wiki title for a file in another tree). Nothing you can see is hidden; the dot says what linking it gets you. The toolbar's link and image buttons write `[]()` or `![]()` with the cursor in the label and the picker open (files, or images); a selection becomes the label and the cursor goes to the destination.

A pick inserts a relative path from the note's folder inside the scope, the external URL (`https://app.lockbook.net/open/<id>`) outside it, and never an absolute path. A wiki pick inserts the shortest title unique in the scope: the name, else enough trailing folders (`[[design/Plan]]`), else the full name likewise, else the whole path from the scope's top (`[[/Plan]]`); for a file past the scope, the shortest title unique in your whole tree. A title with folders in it is read as a path from the note's folder, else as the end of a path anywhere in the scope, nearest first; `/` leads from the scope's top; case and the spaces around segments don't count.

Copy Link puts the file's external URL on the clipboard, any `#fragment` kept and a wiki heading written as its slug: the one form that means the same place wherever it lands. Pasting an `lb://` or external URL into a note writes the note's form: a relative path or the external URL by the rule above, labeled with the file's name or with the selection. A link to a heading of the note being pasted into is just `#slug`, labeled with the heading's text: no rename of the note breaks it. Inside a link begun by hand (`[[`, `](`, a label) or inside code, the URL pastes as it is. A pasted image file links; `![` embeds.

A wiki title nothing matches is a placeholder, drawn in the theme's cyan: opening it creates the note, with any folders its title names, beside the note (`/` from the scope's top), never from a read-only view. A tie stays red.

## Headings
A destination may end in `#…` and open at that heading: its line on the reading line, near the top of the view with room above it, washed for a moment so the eye finds it, a fold hiding it opened. The caret goes after its text, except while reading on touch, where the keyboard is down and moving it would reveal markup the reader didn't ask to edit. Markdown uses GitHub's slug (`[plan](plan.md#next-steps)`, `[up](#next-steps)`), wiki the heading's text (`[[Plan#Next steps]]`, `[[#Next steps]]`), an id link the slug (`https://app.lockbook.net/open/<id>#next-steps`). Repeated headings number as on GitHub (`goals`, `goals-1`), and a wiki link names a repeat by its slug. Opening takes either the slug or the text, case aside. The fragment never changes what a link resolves to or its color; a heading that isn't there opens the file at its top, as a browser does with an anchor it can't find. A web URL's `#` is the site's.

After a `#` the picker lists up to seven headings: of the note the part before the `#` resolves to, or else of every note whose name has that part in it, each heading having what follows. The best come first (starting with it, then the notes in the file picker's order, then document order), shown grouped under each note's name (by folder where two names match). A row is the heading's slug, which tells repeats apart, with the headings above it on the right, shortened from the outside in. A note's row ends in a `#` button that turns the picker to that note's headings, which matters on a phone, where `#` is a keyboard layer away. The note being written reads itself; others come from an index of every note's headings, read once and again for a note only when its content changes.

Hovering a heading on desktop and macOS shows a link glyph after its text that copies its external URL with the slug, as does Copy Heading Link in the right-click menu and, on phones, the edit menu on a heading's line.

On desktop and macOS the outline is a card docked beside the note, in the sidebar's color: its left edge just past the text column, which stays centered while the card fits beside it and otherwise slides left, then narrows. It is as tall as its rows up to the height of the view and scrolls inside when they don't fit, the rows fading out at an edge with more beyond it; it stays in view as the note scrolls. A button in the title bar (desktop) or toolbar (macOS) shows and hides it, lit while it shows, and the choice holds for every note; toggling fades the card and slides the text. Every note offers the outline, headings or not; a note without any says so and how to add one. Where fewer than 560 pt of text would fit beside it, the same card floats over the note's right edge, where it would have docked, and a row, Escape, or a click in the note closes it. On touch it is a sheet from the bottom with rows a thumb tall, from a floating button beside Search on iPhone and iPad, Outline on Android's app bar, and the toolbar while typing on iPhone; floating buttons stand aside while it is open, and Back closes it on Android.

The outline marks the caret's section after you type or move the caret, while the caret is on screen, and otherwise the section being read: the last heading at or above the reading line. That line sits near the top of the view and, over the last screen of scrolling, slides down to the note's last line, so every section near the end gets its turn, in order. Opening at a heading scrolls to where the reading line meets it, lower on the screen near the end, a later heading never landing above an earlier one, so the heading opened is the one marked. The marked row is followed into view, and a row jumps to its heading. An `open/` URL opened from outside the app keeps its heading on iOS, macOS, and Android.

## Backlinks
The outline has a second section, Backlinks, in the card on desktop and macOS and in the sheet on touch: every note with a link that reaches this one, by path, each link with the words around it and its own words in the text color. A note's row opens it; a link's row opens the note landing on the link as a heading link lands, in a new tab with ⌘. The section is always there; with nothing linking here it says so and how to add a link. Links are read from an index of every note's headings and links, built once and again for a note when its content changes; what each link reaches is worked out again after the notes or the tree change, which takes a few milliseconds for a thousand notes.

## Changes that move links
Renames, moves, deletes, creates, and shares go through the workspace, which works out what the change does to links before making it, by resolving them in the tree as it would be. A link that would stop reaching its file, or reach another one (a new or renamed note taking a wiki title), gets an edit to its destination, in the form it's written in, heading kept: the relative path from where things will be, the shortest wiki title that names the file, an absolute path's new path. Each edit is checked to reach the file it reaches now. A link in a note you can't edit, with no form that reaches the file from there, or whose destination isn't written in the link as it reads (a reference link, an escaped spelling) is listed as one that will break. Edits are never made without asking: the desktop rename, move, and create sheets show "Update 3 links in log and roadmap" with a switch that remembers your last choice, a drop onto a folder that would touch links opens the move sheet first, and the delete sheet names the notes whose links will break. Writes merge with whatever the note holds by then. Sync never edits links.

A share is checked under the scope it will make: a link inside what's shared that opens the same file for everyone now and won't then is listed by note, naming the people. For files you own, a switch shares them with the same people too and changes the path links to them into external URLs, so the links open; wiki links to them stay as they are. Desktop shows all of this; touch and the agent will use the same workspace calls once their screens are designed.

## Broken, missing, unshared
Obsidian-shaped wiki: people deliberately leave unresolved wiki links as placeholders; several notes pointing at the same missing title are linked together; click creates the note. For wiki links, "cannot resolve" may be normal.

## Fetch
Nothing is fetched from the web unless you allow it: someone can put a URL in a note they share with you, and if we fetch on render, that site learns you opened the note. One switch, Load web images and link previews, off by default, covers previews and images in every note, your own included. While it's off a web image is a chip with a globe and "Click to load"; a click loads that one.

## Getting an image in
Support all the usual ways, especially on mobile (camera, paste, picker, share sheet). Drop onto the editor is a design goal.

## Attachments
Grouping attachments is good. Constraints:
- Sharing a note should share its attachments as one extra unit, not a slew of unrelated shares.
- Ideally attachments are per note, not one folder for every file in the parent — otherwise you cannot share note A without note B's images.
- Links need a path that still resolves, including in Shared with me.

Pasted images land in a sibling `imports/` folder today; the name is not intuitive, and the path is not frozen.

## Embeds
`![[title]]` embeds the file a wiki title names. A title ending in an image's extension (or `.svg`) is an image, and everything `![]()` is: one glyph in the wrap, green, hidden, or red by the same rules, Edit selecting what is between the brackets, with Obsidian's `|W` or `|WxH` after the pipe as its size. Any other embed (`![[Plan]]`, `![[Plan#Goals]]`, `![[paper.pdf]]`) is the wiki link it names. Renames and moves rewrite an embed as they do a wiki link, `!` kept.

We are open to embedding more than images. It is oddly specific that an image embeds and a drawing or a table file does not — we already show arbitrary tab types in search previews. SVG is particularly exciting.
